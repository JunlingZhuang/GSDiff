### 5.2 Supervisor + 角色专精（来自 Text2BIM / Chen & Bao）

证据显示角色专精是设计 agent 的成熟分工：

| 角色 | 职责 | 模型档次 |
|------|------|---------|
| Supervisor | 路由/委派，决定 what，不干活 | 前沿模型 |
| Encoder | 需求 → 结构化 program（DQL"数字基因"） | 中档 |
| Generator | Gemini 出色块图（typology 注入 CoT） | VLM |
| Reviewer/Corrector | 读结构化违规 → 提出最小局部修改 | 中档 |
| Evaluator | 跑确定性校验工具 | 确定性代码 |

**成本优化**：Supervisor 用前沿模型、worker 用便宜模型，可省约 60% 开销。

### 5.3 纠错循环纪律（不可妥协，证据支撑）

1. **外部验证器驱动**：每轮带具体量化违规（"房间R3与R4重叠0.4㎡；门D2宽0.7m<要求1.2m"），不是"重试"。
2. **批量改**：一次限制同时改动数量，防止改A坏B。
3. **Reflexion 式记忆**：记住改过什么，防来回横跳。
4. **硬上限写进 typed state，绝不写 prompt**（有工程案例因写 prompt 跑47轮烧$180）。起始 3–5 轮。
5. **触顶返回"违规最少版"**，不是最后一版。
6. **违规数不单调下降 → 转人工**，别继续烧 token。
7. **禁止 Reviewer 整体重写**（Text2BIM 记录的失败模式：会让违规数爆炸）——强制单元素局部编辑。

### 5.4 退回机制（三种 + time travel）

| 机制 | 场景 | 实现 |
|------|------|------|
| 用户指定退回 | 点"重新生成"按钮 | 条件边写死路由 |
| agent 自主退回 | 诊断违规根因决定退多远 | LLM 软路由 |
| 混合（推荐） | LLM 诊断 + 人确认 | interrupt + 人拍板 |
| 事后回溯 | "回到第2版" | time travel（get_state_history + checkpoint_id） |

**边界**：退回点可放给 agent，但"是否合规、有无上限、退回后是否重校验"必须写死。计数器触顶强制转人工，防死循环。

### 5.5 Planning 分层

- **外层主流程**：不动态 planning，固定状态机（红线所在）。
- **生成环节内部**：必须 planning——把"生成 healthcare 平面"按功能分区动态拆解（ADaPT 的 as-needed 递归：whole-plan 校验失败才递归到房间级）。
- **编辑/纠错**：各需一次小 planning（复合指令拆 op 序列、违规修复排序）。

### 5.6 多 Agent 扩展策略

> **核心原则**：加 agent 是为解决具体问题（上下文隔离/专业分工/并行），不是因为"显得高级"。每个 agent 都是成本（token/延迟/复杂度/debug难度）和新故障源。**让真实瓶颈触发扩展，别在排期里写死"Phase X 上 multi-agent"。**

#### 5.6.1 你已经是 multi-agent

本系统从 Phase 1 起就是多 agent（5.2 的 Supervisor + 角色专精）：Supervisor / Encoder / Generator / Reviewer / Evaluator。所以问题不是"要不要 multi-agent"，而是"后期要不要扩成更多 agent"。

#### 5.6.2 扩展触发信号（什么瓶颈 → 加什么）

| 信号 | 加什么 agent | 何时 |
|------|------------|------|
| 单 agent 上下文太满（一个 Reviewer 既要懂消防又要懂洁净又要懂结构） | 按专业域拆校验 agent（消防/洁净/无障碍/结构） | Phase 4 最可能 |
| 多科室可并行生成 | 每科室子 agent，Supervisor 调度 | 并行加速需求出现时 |
| healthcare 细分（通用→专科：手术中心/ICU/影像） | 各专科生成专家 agent | 细分专科时 |
| 多规范体系（国标/地方/专项） | 各规范检查 agent | 规范扩展时 |

**不该加的情况**：一个 agent 能干好的拆成两个（只增协调成本）；为"架构看起来分布式"而拆；线性流程不需并行/隔离。

#### 5.6.3 关键决策：加 agent vs 加确定性节点

> **healthcare 系统里，大部分"增强"应该是加确定性规则节点，不是加 agent。**

```
遇到"系统不够强"时，先问：这是该用 LLM 还是确定性代码？

需求：更严格的消防校验
   ❌ 加"消防 agent"(LLM判合规 → 不可靠，违反红线)
   ✅ 加确定性消防规则引擎节点(代码判定 → 可靠)

需求：并行生成多科室
   ✅ 适合加子 agent(并行 + 上下文隔离)

需求：支持新建筑规范
   ✅ 加规则模块(确定性)，不是加 agent
```

**agent 只在需要"语义理解 + 多步规划 + 上下文隔离 + 并行"时才加**；确定性的事（校验/红线）永远是代码节点，不是 agent。呼应核心哲学：LLM/agent 管语义和结构，确定性代码管精确和合规。

#### 5.6.4 多 agent 的代价与红线（扩展时必记）

1. **成本爆炸**：agent 越多，token/延迟越高（工程案例 supervisor 递归失控烧 $180）。每加一个 agent，递归上限和成本重新审视。
2. **协调开销**：agent 间信息会失真/重复（Text2BIM 的 Reviewer 整体重写致违规爆炸）。交接点是新故障源。
3. **debug 变难**：5 个 agent 互调出错要追轨迹 → **这是 LangSmith trajectory 追踪越发重要的原因**。
4. **可控性下降**：agent 越多越自主，越难守 healthcare 合规红线 → 确定性的事别拆成 agent。
