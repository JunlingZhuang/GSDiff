# 用户场景设计

> Healthcare Floor Plan Agent 开发计划（拆分版）｜ [← 总览与文档地图](README.md)

> 如何引导用户输入——从最少信息切入，逐步补充。

### 12.1 切入点策略：从 room/apartment count 引导

不要一上来要求用户填一堆参数。从**最小可用输入**切入，agent 主动追问缺口：

```
用户："我要一个社区诊所"
   │
   ▼
agent 识别信息不足，主动引导（present_options / ask_clarification）：
   "诊所规模大概多少？"  [小型 5-8 间] [中型 10-15 间] [大型 20+ 间]
   │
   ▼
用户选"中型"
   │
   ▼
agent 用 typology 库补全合理默认（必备科室/邻接），生成初稿
   │
   ▼
"已按中型诊所典型配置生成，含：候诊/诊室×8/检验/药房...
 需要调整科室数量或加专科吗？"
```

### 12.2 渐进式信息收集

| 阶段 | agent 行为 |
|------|-----------|
| 冷启动 | 从 count/类型等最小输入切入，typology 库补默认 |
| 澄清 | 仅在关键缺口追问（用按钮选项降低输入成本） |
| 补充 | 用户可随时追加约束（"加个隔离病房"） |
| 边界输入 | 用户能输入/拖拽房间边界，agent 在其上生成/调整 |

### 12.3 用户能力清单

| 能力 | 实现 |
|------|------|
| 自然语言生成 | "生成一个三层诊所" |
| 自然语言编辑 | "把所有病房朝南" → agent 拆 op |
| 输入房间边界 | 用户在画布画/拖边界 → 作为生成约束 |
| 直接拖拽编辑 | 拖墙/改房间 → op → 校验 |
| agent 改边界 | "把卧室扩大1米" → agent 改坐标→校验 |
| 中途反悔 | interrupt 退回 / time travel 回版本 |
| 多方案选择 | agent 给多预览供选 |

### 12.4 边界输入 + agent 修改的协同

用户画一个外轮廓边界 → agent 在边界内规划房间（Graph2Plan 的 boundary-conditioned 模式）→ 用户拖动某房间 → agent 重新平衡其余布局并校验。用户和 agent 在同一数据模型上协作，都走统一 CRUD。

### 12.5 前端渲染选型与接口契约

> **前端实现不在本后端项目范围**，但渲染库的**许可证决策**和**后端该提供的接口契约**与本项目相关，留档于此。

#### 12.5.1 渲染库选型：react-konva（MIT，免费）

**结论：用 react-konva。** 不仅技术合适，更因 MIT 许可证对 healthcare 合规场景是干净选择（零成本、零授权风险、零水印、零数据回传）。

| 库 | 许可证 | 商用免费 | 对你 |
|----|--------|---------|------|
| **react-konva / Konva** | **MIT** | ✅ 完全免费无限制 | ★★ 首选，CAD 例子多，React 契合 |
| Fabric.js | MIT | ✅ 完全免费 | ★ 备选，功能相近 |
| tldraw | 自有 SDK License | ⚠️ **否** | 避开（见下） |
| Excalidraw | MIT | ✅ 免费 | ✗ 白板基因，精确 CAD 费劲 |

**tldraw 为何避开**（尽管它 undo/selection/agent 集成"白送"很诱人）：
- 生产环境必须有 license key，部署即绕不开授权
- 免费档强制"made with tldraw"水印；去水印需商业 license（startup 档 ~$6,000/年起，10人）
- 含技术强制措施 + 向 tldraw 回传使用数据 → **healthcare 合规/数据治理审查麻烦**
- license 自动终止条款（违约或对其发起 IP 主张即终止）→ 商业产品风险

**权衡逻辑**：tldraw 省下的是"一次性开发工作量"，付出的是"持续 $6k/年 + 水印 + 数据回传 + 合规风险"。对长期运营、要过合规的 healthcare 产品，**"一次性写、永久免费可控" 优于 "省事但持续付费 + 授权绑定"**。

#### 12.5.2 分工：库底层 + AI 写业务层

```
react-konva 负责（验证过的底层积木，不自己造）：
   canvas 渲染 / 命中检测 / 拖拽 / pan-zoom / 变换手柄

你 + AI 负责（业务层，AI 加速）：
   吸附规则(snap) / 数据同步 / CAD 语义(墙·门窗) / agentic UI / undo-redo
```

**不要让 AI from scratch 造 canvas 底层**（等于重造 Konva 的劣化版，且命中检测/坐标变换是最易出隐蔽 bug 处）。**正确用法：AI 基于 react-konva 写业务层**——吸附逻辑、WebSocket 同步、高亮/预览组件、undo 栈，这些是 AI 强项。

#### 12.5.3 难度预期

| 部分 | 难度 | 说明 |
|------|------|------|
| 渲染 | 简单 | 库搞定 |
| 基础交互(选/拖/缩放) | 中等 | 库帮大忙 |
| 吸附/对齐手感 | **难** | 反复打磨，决定"专业工具 vs demo" |
| 数据同步 + agentic UI | 中等偏难 | 本项目特有(对接后端 agent + 幽灵预览) |
| 性能 | 简单 | healthcare 量级(几百~几千元素)用不着 WASM |

**WASM 不需要**：元素量级不够大，且重几何计算都在后端 Shapely，前端只渲染+交互。性能阶梯 Canvas→视口裁剪→WebGL(PixiJS) 即封顶，到不了 WASM。

#### 12.5.4 后端接口契约（你的活，决定前端好不好做）

| 后端提供 | 让前端能 |
|---------|---------|
| 带 id 的结构化 JSON | 精确选中/diff 单个元素 |
| 增量事件(`room_updated` 非全量) | 局部重绘，不重画全图 |
| version 乐观锁 | 拖拽乐观更新 + 校验回滚 |
| 门窗挂墙关系式数据 | 墙动门跟随(前端不用自己算) |
| agentic UI 事件(highlight/预览) | 实现引导/预览层 |

**关键**：后端的增量数据接口比前端用什么库更决定流畅度——你已设计对。若未来仍遇性能瓶颈，解法在后端预计算(三角化/LOD)，而非前端 WASM。
